I did not use ACCEPT/WATCH for anything: every finding had a fixed version and the fix is just a tag bump, so there was no reason to carry the risk. No `.trivyignore`.

### a) severity is one input
Reachability (is the vulnerable function really called: `net/http` in stdlib - yes, `zlib` in a static Go app - probably no), is there a public exploit / is it in KEV, and where it runs (public internet or internal, what data is there, is there some other layer like WAF). A HIGH in a library that is never loaded can be less urgent than a MEDIUM on the public endpoint.

### b) distroless / minimal base
You can not exploit what is not in the image. No shell, no package manager, no libs = fewer CVEs and fewer tools for an attacker after RCE. Here: the Go binary is static, and alpine only gave me openssl/musl/zlib which the app doesnt use, and they were more than a half of the findings.

### c) .trivyignore
Right when it is a documented decision: the finding is a false positive or not reachable, with a reason, a ticket and an expiry date. Theater when it is used just to make the pipeline green and nobody looks at it again.

### d) SBOM
When the next Log4Shell happens, I can grep the SBOMs of all shipped images and know "am I affected and where" in minutes, instead of unpacking images and guessing what is inside. Without it, the answer takes days.

## Task 2

Reports: [before](../security/zap-before/report.html) ([json](../security/zap-before/report.json)), [after](../security/zap-after/report.html) ([json](../security/zap-after/report.json)). Passive `zap-baseline.py -t http://qn:8080/notes`, no active scan. QuickNotes returns 404 on `/`, so I pointed ZAP at `/notes` (the spider warning about `/` is expected).

### Triage (before, `quicknotes:lab6`)

| ID | Name | Risk | URL | Disposition |
|---|---|---|---|---|
| 10021 | X-Content-Type-Options Header Missing | Low | `/notes` | **FIX**: `nosniff` in middleware |
| 10049 | Storable and Cacheable Content | Informational | `/`, `/notes`, `/robots.txt`, `/sitemap.xml` | **FIX**: `Cache-Control: no-store` (notes can be private) |
| 90004 | Insufficient Site Isolation Against Spectre | Low | `/notes` | **FIX**: `Cross-Origin-Resource-Policy: same-origin` |
| 10116 | ZAP is Out of Date | Informational | `/` | **FALSE POSITIVE**: it is about the scanner version I pinned, not about QuickNotes. Re-check when I bump ZAP (by 2027-03-31) |

### The fix

[app/security.go](../app/security.go): middleware `securityHeaders(next http.Handler)`. `Routes()` now returns `securityHeaders(mux)`, so it wraps the whole mux, including 404/405 that the mux makes itself and not my handlers. Headers: CSP `default-src 'none'; frame-ancestors 'none'`, `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, `Cross-Origin-Resource-Policy: same-origin`, `Permissions-Policy`, `Cache-Control: no-store`.

Test: [app/security_test.go](../app/security_test.go) sends 8 requests (health, metrics, notes, 200/404/400 from handlers, 404/405 from the mux) and checks the headers. I checked that it fails without the middleware (`return mux` instead of `return securityHeaders(mux)`): every request reports empty headers. With the middleware `go test` passes.

```

Before it was `WARN-NEW: 4 ... Disposition: **ACCEPT** (informational, intended behaviour), re-evaluate 2027-03-31. 10116 is the same as before.

### e) middleware
One place, applies to all routes (also future ones and the mux's own 404/405), nobody can forget the header in a new handler. With per-handler `Header().Set` the first new endpoint without it is the hole.

### f) CSP default-src 'none'
It forbids loading anything: scripts, styles, images, fonts, frames, fetch to other origins. A website would be a blank page. QuickNotes is JSON only, a browser never has to render anything from it, so nothing breaks (but it would break e.g. a Swagger UI served from the same app).

### g) accepting without reading
Real findings hide in the noise, the table loses its meaning, and "accepted" without a reason and a date becomes permanent. Also the next scans get ignored because everything is already "accepted". A mark must say why it is not a problem.

### h) reachability
"Module has a CVE" is just presence in `go.mod`; most such CVEs are in functions we never call. govulncheck follows the call graph and reports only what our code can reach, so there are far fewer alerts to triage and each one is more likely real.

### i) pin the scanner
`@latest` means the check changes without a commit from me: new version, new behaviour or a bug, and CI can turn red (or silently green) for a reason that is not my code. Also it is a supply chain risk, the same idea as pinning actions by SHA.

### j) what govulncheck does not see
OS packages in the image (openssl, musl, zlib - that was most of the Trivy output), the base image, non-Go files, misconfigurations in Dockerfile/compose, secrets. It only knows Go modules and stdlib that our code reaches.
